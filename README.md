# Go (Gin) + React

Простое приложение: бэкенд на **Go (Gin)**, фронтенд на **React (Vite)**.
React-приложение работает **через Go-сервер**: он раздаёт собранный фронтенд и обслуживает API.

## Структура

```
├── server/    # Go-бэкенд (Gin): API + раздача статики React
│   └── migrations/  # версионированные миграции БД (goose, SQL)
├── frontend/  # React-приложение (Vite)
└── README.md
```

## Миграции БД (goose)

Схема базы управляется **goose** (`github.com/pressly/goose/v3`):

- Миграции — SQL-файлы в `server/migrations/`, имя `NNNNN_name.sql`
  (числовой префикс = версия).
- Файлы **встроены в бинарник** (`//go:embed`), поэтому отдельный шаг деплоя
  не нужен: при старте сервер сам применяет неприменённые миграции
  (создаётся таблица `goose_db_version`).
- Применяются до загрузки хранилищ в память: `initDB → runMigrations → init*`.

Как добавить новую миграцию:

```sql
-- server/migrations/00006_my_change.sql
-- +goose Up
ALTER TABLE ...;

-- +goose Down
ALTER TABLE ...;
```

Затем обычный деплой (`make deploy`) — миграция применится при следующем старте.
На уже существующих базах миграции `00001–00005` идемпотентны
(`IF NOT EXISTS`/`ON CONFLICT`) — они лишь фиксируют текущую схему в goose.

## Быстрый старт

### 1. Запустить бэкенд

```bash
cd server
go mod tidy
go run .
# Сервер: http://localhost:8080
```

### 2. Разработка фронтенда (hot-reload)

```bash
cd frontend
npm install
npm run dev
# Vite: http://localhost:5173
# Запросы /api проксируются на Go-сервер (см. vite.config.js)
```

### 3. Сборка и запуск «по-настоящему» через Go

```bash
cd frontend
npm run build        # соберёт фронтенд в frontend/dist

cd ../server
go run .             # Go-сервер отдаёт и страницу, и API на :8080
```

Откройте http://localhost:8080 — фронтенд отдаётся Go-сервером,
а данные загружаются с `/api/health` и `/api/message`.

## Горячая перезагрузка Go-сервера (air)

`make dev` запускает Vite (HMR) и Go-сервер. Для Go-сервера работает
**авто-перезагрузка через [air](https://github.com/air-verse/air)**: изменение
`.go`/`.sql` файлов пересобирает и перезапускает сервер (конфиг —
`server/.air.toml`). Установка:

```bash
go install github.com/air-verse/air@latest
```

Если air не установлен, `make dev` работает как раньше: обычный `go run .`
без авто-рестарта (в логах появится подсказка).

## Переменные окружения

- `PORT` — порт сервера (по умолчанию `8080`)
- `GIN_MODE=release` — release-режим Gin
- `DEEPSEEK_API_KEY` — ключ DeepSeek для генерации конспектов и резюме
- `DATABASE_URL` — строка подключения PostgreSQL
- `YANDEX_FOLDER_ID` — ID каталога Yandex Cloud для SpeechKit
- `YANDEX_IAM_TOKEN` — IAM-токен Yandex Cloud (способ аутентификации №1)
- `YANDEX_API_KEY` — статический API-ключ Yandex Cloud (способ аутентификации №2)
- `YANDEX_TTS_FORMAT` — формат аудио (`oggopus`, `mp3`, `lpcm`; по умолчанию `oggopus`)
- `YANDEX_TTS_VOICE` — голос синтеза (по умолчанию `oksana`; варианты: `alena`, `filipp`, `jane` и др.)
- `YANDEX_TTS_SPEED` — скорость речи (например, `1.0`, `1.5`)

## Агент по задачам (dev)

В dev-режиме агент забирает задачи из раздела «Приложение» с продакшен-сервера
и выполняет их в локальном репозитории через DeepSeek (читает/пишет файлы,
запускает сборки и тесты), после чего обновляет статус задачи.

Агент запускается **отдельным процессом** (`AVAKUMOV_AGENT=1`), а не внутри
Go-сервера: он сам правит файлы (код, миграции), и если бы он жил в сервере,
air перезапускал бы его при каждом изменении файла посреди задачи.
`make dev` / `make dev-backend` поднимают агента сами, отдельно есть
`make dev-agent`. В production агент не запускается (нет исходников и
`GIN_MODE=release`).

**Кнопка «Deploy»**: у задачи со статусом «Готова» в UI есть кнопка
«Deploy» — она ставит флаг `deploy_requested`. Dev-агент при следующем опросе
видит запрос, коммитит изменения в рабочем дереве (сообщение с номером
задачи) и запускает `make deploy`. По итогу проставляет время деплоя
(`deployed_at`) и дописывает вывод в журнал задачи. Сам LLM деплой запускать
не может: `make deploy`/`deploy.sh`/`git push` запрещены в инструменте
`run_command`.

**Безопасная работа с git**: задачи выполняются **только в чистое рабочее
дерево** — если есть незакоммиченные файлы, задача получает статус
«Не выполнена» с перечнем файлов, а выполнение откладывается. Каждая
успешная задача коммитится **отдельным коммитом**, хэш сохраняется в задаче
(`commit_hash`). После неудачной задачи дерево автоматически подчищается
(`git restore .` + `git clean -fd`).

**Кнопка «Откатить»**: у задеплоенной задачи можно запросить откат
(`revert_requested`) — агент делает `git revert` коммита задачи,
передеплоивает через `make deploy` и проставляет `reverted_at`.

Переменные окружения:

- `AGENT_SERVER_URL` — сервер задач (по умолчанию `https://avakumov.ru`)
- `AGENT_USERNAME` / `AGENT_PASSWORD` — учётные данные на сервере задач
- `AGENT_POLL_INTERVAL` — период опроса в секундах (по умолчанию `120`)
- `AGENT_REPO_ROOT` — корень репозитория (по умолчанию определяется сам:
  каталог запуска, а если это `server/` — на уровень выше)

Нужен также `DEEPSEEK_API_KEY` (для выполнения задач).

## Озвучка конспектов (TTS)

Конспекты знаний можно **прослушивать** — сервер озвучивает текст через
**Yandex SpeechKit v1 REST API** и возвращает аудио. Сгенерированное аудио **сохраняется
в базе данных** (таблица `knowledge_notes_audio`), поэтому повторный запрос не
тратит токены/квоту SpeechKit.

Как это работает:

1. В карточке конспекта нажмите кнопку **«Озвучить»**.
2. Сервер вызывает Yandex SpeechKit, текст конспекта предварительно
   очищается от Markdown-разметки.
3. Аудио сохраняется в БД и возвращается браузеру — в карточке появляется
   аудио-плеер.
4. При повторном открытии карточки плеер подгружается мгновенно, без вызова
   SpeechKit.

Длинные конспекты автоматически разбиваются на фрагменты и синтезируются
частями, затем склеиваются в единый файл.

### Настройка

Нужны переменные окружения (см. выше):

- `YANDEX_FOLDER_ID` — ID каталога Yandex Cloud;
- `YANDEX_IAM_TOKEN` или `YANDEX_API_KEY` — один из способов аутентификации;
- опционально `YANDEX_TTS_FORMAT`, `YANDEX_TTS_VOICE`, `YANDEX_TTS_SPEED`.

Аудио хранится в таблице `knowledge_notes_audio` (BYTEA-колонка `data`) и
удаляется автоматически (каскадно) при удалении самого конспекта.

## Деплой

Приложение собирается в **один исполняемый файл**: Go-бэкенд включает в себя
собранный React-фронтенд через `//go:embed` (бинарь ничего не ищет на диске).
Запускается как **systemd**-сервис, наружу наружу смотрит **Caddy** (HTTPS +
реверс-прокси на локальный порт).

### Сценарий `deploy.sh`

Скрипт в корне проекта выполняет всё автоматически:

1. Собирает фронтенд (`frontend/dist`).
2. Копирует его в `server/frontend-dist` и встраивает в бинарь (тег `embed`).
3. Собирает один бинарник в темповый каталог.
4. Ставит его в `/opt/avakumov/server`, создаёт служебного пользователя.
5. Создаёт и активирует systemd-юнит `avakumov.service`.
6. Прописывает домен в Caddy и перезапускает его.

По умолчанию деплой выполняется на **текущую машину** (не на удалённый VPS).
Нужны `sudo`, `go`, `node/npm` и `systemd`.

```bash
# Деплой с интерактивным вводом домена
./deploy.sh

# Деплой с готовым доменом
DOMAIN=example.com ./deploy.sh

# Деплой + установка Caddy и служебного пользователя
./deploy.sh --install-deps
```

Удобно через Makefile:

```bash
make deploy          # ./deploy.sh
make deploy-deps     # ./deploy.sh --install-deps
```

### После деплоя

```bash
systemctl status avakumov     # статус сервиса
journalctl -u avakumov -f     # логи
```

### Полезные команды

`make build-binary` — просто собрать один бинарник со встроенным фронтендом
(без установки на машину) в `server/server`.

### Как работает embed

- `server/embed.go`      — реальный embed (только для `-tags embed`).
- `server/embed_stub.go` — пустая заглушка для обычной разработки.
- `server/frontend-dist` — сюда скрипт кладёт статику перед сборкой.

При локальной разработке (`go run .` без тега) сервер использует фолбэк на
файловую систему `../frontend/dist`. В проде — только содержимое бинарника.
